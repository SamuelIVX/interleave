## TL;DR

Task #10 remains complete. This document plans only the leftover report JSON escaping defect,
the narrower boundaries identified in the post-#10 audit, and its two highlighted verification
gaps. It does not activate the explicitly deferred/conditional roadmap work.

Start with three independently reviewable bundles: **A — report JSON escaping**, **B — focused
symmetry assurance**, then **C — explorer residual triage**. B combines V1/B2 below; those rows do
not require separate PRs. The other rows are proposed support expansions or contract checks,
not confirmed bugs or approved implementation promises.

Recheck the cited symbols and specs before implementation; this is a planning inventory, not an
execution spec. No implementation is included in this document.

## Scope and estimates

- Exclude roadmap **#8, #11, #12, 9-V5, 9-V6, 9-F1, 9-F5–F8 and 9-F10–F11**. Keep their existing
  deferred/conditional decisions. In particular, no dynamic spawning, cyclic/unbounded execution,
  weak memory, Java bytecode ingestion, formal proof project or general DPOR representation rewrite.
- Existing source caps stay fixed. Any extension below must preserve finite execution and work
  bounds. A larger-cap project would reopen excluded 9-F1.
- **LOE rank is ascending effort, not priority.** Estimates are focused developer days, including
  relevant tests/docs/local verification; they exclude waiting for CI or reviewers. **S:** up to
  one day; **S–M:** 1–3 days; **M–L:** 3–10 days; **L:** about 1–2 weeks; **XL:** several weeks.
  These are planning estimates, not delivery commitments.
- **Simple spec:** one focused behavior/verification contract. **Spec-set:** interacting contracts
  needing separate treatment, such as execution semantics, reduction proof, evidence and compatibility.
  A spec-set does not imply one PR per document.
- PR targets bundle the implementation, callers, tests, examples and evidence for one behavior.
  They are provisional. Counts sharing a bundle are not additive; investigation can end with an
  honest limitation instead of a production change. Do not manufacture a kill or a feature to
  satisfy a row.

1. Read `AGENTS.md`, check the current revision and inspect all callers of the touched contract.
   Do not modify the original dirty checkout under `Documents/projects/interleave`.
2. Use independent literal count/outcome/schedule oracles where relevant. Preserve source identities,
   original owner IDs, replay validity, failure/cutoff categories, and representative-visit labeling.
   A successful replay alone does not prove emitted owner IDs are the actual traversal IDs.

   preexisting `%s` null behavior if it is part of an accepted row contract; establish that behavior
   before changing it. Do not broaden the fix into a result-type or nullable-schema migration.
4. Freshly measure mutation targets that change or whose residuals are being triaged. Keep class
   scope, operators, target tests and floors fixed. Record population drift and semantic lineage;
   identical raw instruction indices alone do not identify the same mutation after code insertion.
   Do not sum overlapping scopes or count resource errors as kills.
5. The historic **34** explorer non-kills and other recorded scores are scope/revision snapshots.
   Later PR #119 changes were not a new PIT census. Do not promise to kill all residuals, describe
   them all as bugs, or promote a bounded argument into universal equivalence.
6. Use the repository's local resource limits for every Gradle invocation:

   ```sh
   ./gradlew --max-workers=1 -PpitestThreads=1 build javadoc
   ./gradlew --max-workers=1 -PpitestThreads=1 pitest -PpitestTargetOverride=<affected-class-list>
   ./gradlew --max-workers=1 -PpitestThreads=1 pitest
   ```

   The first command must pass the applicable complete regression suite and strict Javadoc. Run
   scoped mutation checks for selected changed/triaged targets; run the unchanged default gate when
   default state/CBS targets or gate accounting are affected. Scoped aggregate R5/R7 results are
   not a full-scope pass. Add browser checks when producer schemas, normalization or presentation
   change. No new full PIT/browser run is implied by this documentation-only inventory.
7. Apply the existing selective CodeRabbit gate to substantive new implementations. Continue to
   skip CLI reruns for trivial/minor PR feedback. Include proof, callers, tests and required UI/report
   support in the feature PR before enabling a capability. Stop after publishing a PR; Sam supplies
   CI, review and merge updates.

## Scope guard: things that do not become new work here

- More aggressive DPOR representation/subsumption optimization remains parked under **9-V5**;
  B2 is a review/test task for the current conservative algorithm only. Mechanically checked proof
  remains parked under **9-V6**; V1 seeks targeted Java-contract evidence or a scoped argument.
- Existing source budgets are not raised. Helpers remain finite; dynamic spawning, unbounded or
  cyclic execution, liveness, weak memory and actual Java ingestion are excluded.
- Assertion messages/extra assertion arguments and other independently proposed syntax convenience
  features are not folded into B5. A helper extension does not silently enable guarded nesting.
- Preserve representative failure/cutoff witnesses, not every concrete schedule or diagnostic
  multiplicity. Full graph capture is excluded #8. CBS/DPOR counts can include context revisits.
- Native stream rejection remains deliberate. JSON/source compatibility does not promise cross-build
  Java object-stream compatibility or safe deserialization of untrusted artifacts.
- Performance figures from earlier synthetic workloads are not general runtime guarantees. This
  inventory does not activate a new representation rewrite or broader benchmark project.
