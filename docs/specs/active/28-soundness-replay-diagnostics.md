# Spec: Soundness attestation replay and diagnostics

## Objective

Protect the positive replay obligation behind reported VIOLATION rows and the exact diagnostics
that distinguish missing evidence, missing models and replayed non-violations. Continue roadmap
9-V1 after Spec 27 without mixing report rendering or changing replay semantics.

## Scope

- Add `SoundnessReplayTest` in the report package.
- Correct `SoundnessAttestation` class Javadoc to describe optional invariants, authentic source
  runtime errors and propagated replay exceptions. Executable production code is unchanged.
- Ship this specification and update the future-work roadmap.
- Leave public APIs, dependencies, mutation operators/scope, exclusions and score floors unchanged.

## Non-Goals

Markdown rendering, new explorer/reduction or serialization contracts, mandatory invariants,
exception-to-attestation conversion and algorithm changes belong to separate work. This contract
does not assert that an execution-only attestation establishes a property violation.

## Invariants

- Exact verdict validation precedes the replay phase; a verdict failure stops the attestation before
  replay diagnostics. Replay requirements below assume verdict validation succeeds unless explicitly
  testing that precedence.
- A reported violation is a positive replay obligation, even with bitstate storage or bounded search.
- Supplied invariants are evaluated against the replayed state, not the initial configuration.
- Authentic source runtime failures can leave the invariant true because atomic writes roll back.
  Replay must authenticate the failure before the runtime-error exception is accepted.
- Without a supplied invariant, legacy replay checks execution but does not establish terminal
  classification. Preserve that compatibility rather than claim a stronger soundness proof.
- Replay corruption propagates; it is not silently converted into a successful attestation.
- Assertion failures count as mutation kills; timeout/error detections do not.

## Requirements

1. After the exact-verdict phase succeeds, every reporting strategy/store pair SHALL reject a
   VIOLATION without a failing trace, naming the subject, strategy and store in the complete
   diagnostic. Exact DFS expectation and cross-strategy mismatches take precedence over missing-trace
   diagnostics. A bitstate DFS row skips verdict matching and reaches the missing-trace check.
2. A VIOLATION with a trace but no registered program SHALL fail with the unknown-subject reason,
   including bitstate rows excluded from verdict matching.
3. A genuine legacy trace SHALL pass with no failure reason when the property holds initially
   and fails after its recorded write. A counterfeit trace SHALL fail with the complete subject,
   strategy and store diagnostic when the property is false initially but holds after replay.
4. Legacy step-outcome corruption SHALL propagate with the recorded/actual outcome diagnostic.
   Absent-invariant execution-only compatibility SHALL retain a null success reason.
5. Authentic source property failures and authenticated source runtime failures SHALL pass.
   A runtime fixture SHALL retain the last committed value after a later atomic block fails.
6. Forged source terminal verdicts and runtime categories SHALL propagate replay corruption,
   demonstrating that the attester supplies the registered invariant and authenticates evidence.
7. Compare baseline/final semantic mutation identities and statuses. Preserve every baseline kill;
   retain explicit rendering/bookkeeping dispositions without exclusions or private-call assertions.

## Design and Tests

The reporting matrix is the four existing strategy labels crossed with EXACT/BITSTATE. These
labels exercise attestation policy, not a claim that each row was generated by that explorer.
Legacy witnesses execute one actual WriteCounterStep from counter zero to one. Opposing predicates
on that state distinguish genuine violations from replayed non-violations and from initial-state
checks. Source witnesses come from the real loader and DFS; forged cases alter one terminal field
or failure category. Expected diagnostic strings are literal templates independent of production.

| Requirement | Regression | Cases |
|---|---|---|
| R1 | `missingTraceReportsSubjectStrategyAndStore` | Eight strategy/store pairs |
| R1 | `missingTraceDiagnosticRespectsVerdictPrecedence` | Exact/bitstate DFS VIOLATION without a trace, registered expectation PASS |
| R2 | `unknownProgramReportsSubject` | Both stores |
| R3 | `genuineLegacyViolationPasses` | Eight strategy/store pairs |
| R3 | `replayedNonViolationReportsSubjectStrategyAndStore` | Eight strategy/store pairs |
| R3 | `laterCounterfeitViolationStillFails` | Both stores after a genuine first replay |
| R4 | `corruptLegacyOutcomePropagates` | Both stores |
| R4 | `absentInvariantRetainsExecutionOnlyCompatibility` | Both stores |
| R5 | `authenticSourceRuntimeFailurePassesWithTrueInvariant` | Both stores; committed 7 survives tentative 9 and modulo-by-zero |
| R5 | `authenticSourcePropertyFailurePasses` | Both stores |
| R6 | `forgedSourceTerminalVerdictPropagates` | Both stores |
| R6 | `forgedSourceRuntimeEvidencePropagates` | Both stores |
